# Curriculum — Shared, Undated, Ordered Sequence (Plan Source for Capture)

`calendarEvent` (ADR-0007) already carries day-ahead planned activities — `startDate`/`endDate`, `sessionTypeId`, `subThemeId`, `indoor`, `location`, `itemsToBring`, `permissionRequired`, `sortOrder`. So "curriculum" does not fill a _scheduling_ gap; calendarEvent owns that. The real gap is the **plan source** the daily-capture flow needs: a reusable, ordered, _shared_ learning sequence that feeds the DCR's `wasPlanned`/`deviation` machinery, which today has no link at all — the capture page hardcodes `initialActivities={[]}` (`src/app/dashboard/owner/daily/capture/[sessionId]/page.tsx:68`) despite `getCalendarEventsForDcr` already fetching planned items.

Two authoring lifecycles are conflated under "event": **curriculum** = batch-planned pedagogy core, authored for a range (week → semester); **event** = rare ad-hoc one-off (an outing to a new `location`, something needing `permissionRequired`). Creating day-to-day activities one-by-one as "events" defeats the "event" terminology — call the backbone curriculum, reserve "event" for the uncommon.

**Decision — one new table, one new column, no projection engine:**

1. **`curriculum` (undated, shared, ordered, per-term).** `id, termId (FK→term, NOT NULL), sortOrder (int, the "day 21" ordinal — reorderable), subThemeId (FK→subTheme, NOT NULL), name (text, NOT NULL), objective (text, nullable — the one pedagogical delta), indoor (bool, default false), itemsToBring (text, nullable), + createdAt/updatedAt/deletedAt`. **No `date` column. No `sessionTypeId` column** — the sequence is shared across every session; each consumes it at its own pace. Per-term scope (`termId NOT NULL`) matches holiday/monthly/quarterly tables and encodes "day 27 of the current term."

2. **`dailyClassReport` gains one nullable FK: `curriculumId` (FK→curriculum, nullable).** The DCR _is_ the dated, session-scoped instance — it already carries `date + sessionTypeId` and `unique(date, sessionTypeId)` (ADR-0007). The FK is "the lock": which curriculum item this session was on for this capture day. Nullable so captures with no plan (spontaneous days, mid-migration) survive. `dcrActivity` is **unchanged** — its planned core references curriculum transitively through the DCR; per-activity `wasPlanned=false` rows (the existing "Tambah Aktivitas Tidak Terencana" flow) carry no link.

3. **"Next for a session" is a query, not a stamp job.** For session X, the next curriculum item = the lowest-`sortOrder` row whose `id` is not already locked by any `dailyClassReport` row for `sessionTypeId = X`. Session position is implicit in capture history — DCR progress _is_ the position. No `curriculumPosition` pointer, no join table, no sync-on-capture logic.

4. **No projection engine, no instance table, no drift policy.** This is what separates the decision from the "blueprint + projection" alternative. The heavy part of that alternative was never the undated template (cheap, kept here) — it was stamping instances onto calendar dates (weekday × holiday-skip × loop rules), the instance table to hold them, and the re-projection policy when an owner edits a stamped instance. All three collapse: the DCR plays the instance role, captures lock the _id_ (not a date or sortOrder), and editing curriculum never rewrites what a captured DCR points at.

5. **Reorder guard is forward-looking only.** Because the DCR locks `curriculumId` (the id), reordering `sortOrder` cannot scramble a captured DCR — it reads by id. So "only reorder days that haven't happened yet" does not protect history (the id-link already does); it is a forward guard against yanking the rug from under a session that hasn't reached an item yet (would make it skip or stutter). Reorder freely for items no session has consumed; never need to touch captured ones.

6. **Curriculum / calendarEvent / capture split.** curriculum = planned pedagogy core (objective, indoor, items-to-bring); calendarEvent = rare ad-hoc one-off (location, permissionRequired, ranged endDate) — stays rare, "event" terminology preserved; dailyClassReport = dated capture + the lock. The capture page reads curriculum for the planned core (`getNextCurriculumForSession`) and calendarEvent for the **exception layer** (an outing/permission on top of the planned day).

**Verification.** Additive migration only — new `curriculum` table + nullable `curriculumId` on `dailyClassReport`; no existing column dropped. On the DB-schema confirmation gate: `bun run db:generate` → `bun run db:migrate`, then verify a relation query (`with: { curriculum }` on a DCR) resolves — a 500 on a `with:` often means the FK column isn't live yet (AGENTS.md gotcha). `bun typecheck` + `bun lint`. The "next for session" query and the reorder-guard UX (warn if a referenced item is being moved) get unit tests; the curriculum _authoring_ form (batch-edit the whole term's ordered list) is a separate iteration, not gated by this ADR. Until the FK lands, daily capture stays on its current hardcoded-empty `initialActivities`.

**Tradeoffs.** We trade the simplicity of "one dated activity table" for a second, undated table — but gain three wins the dated-instance model cannot reach. **(a) No cross-session duplication:** "calligraphy day 21" is one row shared by sessions A, B, and C even when C reaches it two calendar weeks later (C simply has consumed fewer items so far). The dated-instance alternative writes that activity three times — once per session per date — which is the smell that kills it. **(b) No projection machinery:** the DCR-as-instance trick eliminates the engine, the instance table, and the drift policy in one move — the heaviest parts of blueprint+projection, all avoided. **(c) Clean terminology:** "event" stays rare, curriculum owns the day-to-day, and the plan→capture handoff finally has a real link where the DCR today carries only a name string. Accepted costs: the "next for session" read is a derived not-stored position (standard, bounded); re-ordering _un-consumed_ items mid-term shifts every slower session's "next" (acceptable — they haven't reached it); and `itemsToBring` is duplicated across `curriculum` and `calendarEvent` (genuine shared attribute; promoting a curriculum day to an event shouldn't lose it — noted, not normalized at this scale).

**Out of scope.** Cross-term sequence reuse (a future `blueprintId` extension can let a curriculum row reference a prior term's template without rewriting the dated-instance model — deferred, not blocked). The `learningDomain` enum / scope-and-sequence pedagogy layer (fine-motor / social-emotional / cognitive / language / self-help milestones) — deferred; "professionally decent" here is the single `objective` column, not a full objectives system. The exact curriculum authoring UX (list-editor for a term's whole sequence) and the reorder-guard UX are implementation, not decision. Multi-preschool / multi-class scaling is the condition that would re-open the blueprint+projection question; not on the table.

**Cross-reference — descends from ADR-0007.** This decision is a direct child of the calendar-date-anchor model (ADR-0007). ADR-0007 made `date` the universal axis and split `termSession` into `sessionType` + `holiday` + date-anchored capture tables. Curriculum is the one entity that sits **off** the date axis by design — undated and shared — and reaches the date axis _through_ the DCR (the dated instance), which ADR-0007 re-keyed to `(date, sessionTypeId)`. The `unique(date, sessionTypeId)` invariant ADR-0007 placed on `dailyClassReport` is what makes "one curriculum item per session-per-day" (the FK lives on the DCR, not `dcrActivity`) a sound 1:1 — each session consumes one plan item per capture day. Where ADR-0007 said calendarEvent plans day-ahead activities, this ADR refines: calendarEvent plans **ad-hoc exceptions**; curriculum owns the **planned core**, and the capture page reads both (curriculum → `initialActivities`, calendarEvent → exception layer).
